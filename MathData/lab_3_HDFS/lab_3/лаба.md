# Лабораторная работа 3. Переезд: два хранилища «Синицы»

## Легенда

В лабе 2 вы посчитали цену запроса, не запуская его, — по метаданным
файла. Сегодня файлы «Синицы» переезжают туда, где эту цену считает
чужой счётчик: в объектное хранилище. Заодно выясняется, что у банка
есть два хранилища: HDFS, где лежит история операций, и новое
S3-совместимое хранилище, куда едет ваша витрина. Отдел архитектуры
ждёт от вас ответа, что где держать, — с опорой на результаты опытов.

Вы впервые работаете с удалёнными хранилищами стенда. Одинаковые
исходные файлы уже размещены в HDFS и в MinIO — реализации
S3-совместимого хранилища. Проверите на себе, что каждое хранилище
обещает и чего не обещает, сверите фактические байты с прогнозом
из лабы 2 и увидите, как выглядит витрина, опубликованная наполовину.

Правило курса прежнее: **гипотеза → замер → объяснение**. Там, где
в задании написано «сначала предскажите», предсказание записывается
в отчёт *до* запуска команды; несовпавшее предсказание с объяснением
ценится выше совпавшего без него.

## Словарик

| Термин | Значение |
|---|---|
| NameNode / DataNode | узел метаданных / узлы данных HDFS |
| Блок | кусок файла в HDFS (на стенде — 128 МиБ), единица размещения и репликации |
| Edge node | пограничный узел: клиенты и настройки кластера есть, данных нет. У нас — `node1` |
| Бакет, ключ, объект | контейнер, имя-строка и содержимое в объектном хранилище |
| Префикс | начало ключа. «Каталог» в S3 — это префикс, и больше ничего |
| `Range` | заголовок HTTP: «дай байты с N по M» |
| Multipart upload | загрузка объекта частями; новый объект появляется после успешного запроса завершения загрузки |
| Presigned URL | ссылка с подписью и сроком годности: доступ без ключей |
| STS | служба выдачи временных ключей |
| Erasure coding (EC) | защита данных контрольными частями вместо полных копий |
| Витрина | набор данных для аналитических запросов |
| Версия витрины | один законченный результат подготовки витрины |
| Публикация | момент, с которого готовая версия доступна читателям |
| Атомарность | операция либо произошла целиком, либо не произошла; промежуточное состояние не видно |

## Часть 1. HDFS: файл как блоки (на `node1`)

Файлы лабы 2 лежат в HDFS в каталоге `/datasets/sinitsa/` — только
на чтение. Ваш каталог — `/user/<логин>`, квота 5 ГБ. Все команды
этой части выполняйте после входа по SSH под своим логином стенда.
Здесь `$USER` — логин на `node1`; относительный путь `lab3`
в командах `hdfs dfs` означает `/user/$USER/lab3`.

**Задание 1.1 — блоки.** `txn.csv` весит 853 056 883 байта, блок
HDFS — 128 МиБ. **Сначала предскажите**: сколько будет блоков, каков
размер последнего, сколько места данные файла занимают с учётом
трёх реплик. Контрольные суммы и прочие служебные расходы
в расчёте не учитывайте. Затем проверьте:

```bash
hdfs fsck /datasets/sinitsa/txn.csv -files -blocks -locations
hdfs dfs -du -h /datasets/sinitsa/txn.csv
```

В отчёт: предсказание, факт, пояснение двух размеров из `du`
(размер файла и размер с учётом реплик), строка первого блока
с расшифровкой полей (`blk_…`, `len=`, `Live_repl=`, адреса, `DISK`). Сколько места
на диске DataNode занимает последний, неполный блок?

**Задание 1.2 — репликация.** Скопируйте себе файл на два блока
и попросите больше копий, чем есть узлов:

```bash
hdfs dfs -mkdir -p lab3
hdfs dfs -cp /datasets/sinitsa/txn_none.parquet lab3/
hdfs dfs -setrep 5 lab3/txn_none.parquet
hdfs fsck /user/$USER/lab3/txn_none.parquet
hdfs dfs -setrep 3 lab3/txn_none.parquet
```

`setrep` без `-w` меняет требуемое число реплик, но не ждёт его
достижения. Не добавляйте `-w` к запросу пяти реплик: при трёх
DataNode команда будет ждать недостижимого результата.

Что сообщил `fsck` — ошибка это или предупреждение? DataNode у нас три:
на каких узлах лежат реплики любого блока и можно ли на этом стенде
увидеть работу раскладки по стойкам? Что изменилось бы с четвёртым узлом?

**Задание 1.3 — NameNode не в потоке данных.** Узнайте активный
NameNode (`hdfs haadmin -getAllServiceState`). В адресе ниже замените
`<активный>` именем узла из строки `active`, без порта.
Попросите у него содержимое файла по HTTP:


Данных в ответе нет. Какой код вернул сервер, что в заголовке
`Location` и **почему NameNode устроен именно так**? Повторите
ту же команду, добавив `-L`. Объясните, что изменилось
в поведении команды и кто теперь отдаёт байты файла.

**Задание 1.4 — цена файла в памяти.** NameNode держит около 150 байт
на каждый файл, каталог и блок. Двадцать серверов мобильного приложения

события раз в час склеиваются в один файл на все серверы. Сколько
памяти получится в каждом случае?

Для оценки считайте год равным 365 дням, каждый файл непустым
и помещающимся в один блок — в том числе объединённый часовой файл.
Метаданные каталогов не учитывайте. Отдельно выполните

**Задание 1.5 — переименование и дозапись.** Заготовьте каталог
из ста файлов и переименуйте его, с секундомером:

## Часть 5. Витрина, опубликованная наполовину

Вредительский эксперимент. Задача публикует новую версию витрины —

**Задание 5.3 — почините.** Переименования нет. Но запись *одного*

не изменяются; указатель переключается только после завершения
записи всей новой версии. Читатель выбирает текущую версию один раз

**Бонусное задание (необязательное).** Два писателя соревнуются
